Docker Compose runs the full stack: `marketplace_scraper`, `marketplace_filter`, `marketplace_sender`, `marketplace_server` (Django, port 8000), plus `postgres`, `adminer` (port 8081), and `tor_proxy` (SOCKS 9050 / control 9051). The `backup` service is **not** part of that — see below.

**Backups** (`backup/`, [`docs/BACKUPS.md`](docs/BACKUPS.md)): a **one-shot** container built `FROM postgres:15.2` so the `pg_dump` client matches the server by construction. It dumps to `./backups/` (gitignored — dumps hold seller PII), pushes to `restic` if `RESTIC_REPOSITORY` is set, then exits; with it unset the local dump still runs, so it is safe to deploy before off-host storage exists. Dumps use **`-Z0` on purpose** — pg_dump's own compression defeats restic's dedup (measured, `docs/BACKUPS.md` §6.1).

Two things to know before touching it:
- It sits behind a compose **`profiles: ["backup"]`** key, so `docker compose up -d` never starts it and nothing idles between runs. **`docker compose build` silently skips profiled services** — `deploy.yml` builds with `--profile backup`, and dropping that flag leaves the backup image stale forever.
- Scheduling is a **systemd timer** on the Pi (`backup/systemd/`, installed manually), not a loop in the container: `Persistent=true` catches up a backup missed while the Pi was down, which a sleep loop cannot. Force one with `sudo systemctl start marketplace-backup.service`, or `docker compose run --rm backup` directly.

Deliberately *not* a `Job` in the app's queue: backups must survive the app being broken, which is also why failure alerts go through `BACKUP_DISCORD_WEBHOOK_URL` rather than the `Discord` table. Restore procedure is `docs/BACKUPS.md` §9.

**CI/CD** — three workflows. `test.yml` runs `pytest` in one job and `ruff check .` + `mypy .` in a separate `lint` job, on push/PR to `main`. `deploy.yml` fires on a **`v*` tag** and deploys to a self-hosted runner on a Raspberry Pi (`docker compose build` → **verify the built image** (`django.get_version()` + `manage.py check`, before `down`, so a bad build costs no downtime) → `down` → **pre-migration `pg_dump`** → `migrate` → `up -d`); `git tag v1.2.3 && git push origin v1.2.3` is the only deploy path. A failed pre-migration dump **aborts the deploy** — that's intentional, a bad migration is the likeliest data-loss event here.

`contract-check.yml` is the third: weekly (Mondays 06:00 UTC) plus `workflow_dispatch`, it runs `pytest -m live` against the **real** bazos.cz. Cassettes only prove the scraper handles the HTML recorded the day they were made; this re-parses the live site so partial drift (a field quietly disappearing) surfaces here rather than in production. It runs on the **same self-hosted Pi runner** as `deploy.yml` — Bazos refuses GitHub-hosted runner IPs — inside a throwaway `python:3.12-slim` container, which is the sole reason `TEST_DB=sqlite` exists (see Testing below). It shares the Pi's single runner, hence the 20-minute timeout: a stalled live scrape would otherwise block deploys.

**Self-hosted runner prerequisites** (Raspberry Pi, discovered the hard way 2026-08-22 — not needed again until the runner is reprovisioned): the Pi's `docker.io` package (Debian's build, currently 20.10.24) ships neither the Compose v2 nor the `buildx` CLI plugin, so `docker compose --profile backup build` fails outright. Both must be installed manually as CLI plugins (`/usr/local/lib/docker/cli-plugins/docker-compose` and `docker-buildx`, from the `docker/compose` and `docker/buildx` GitHub releases, `*-linux-aarch64`/`*-linux-arm64` respectively) — `apt`'s version is too old to carry them. Separately, the runner's `actions.runner*.service` must be **restarted** after the `user` account is added to the `docker` group — systemd services don't pick up new group membership from an already-running process, so `docker compose` fails with `permission denied ... docker.sock` until the service is bounced (`sudo systemctl restart actions.runner.*.service`), even though `groups` already shows `docker` for interactive SSH sessions.

## Architecture

Django scraper for online marketplaces — primarily the Czech **Bazos.cz**, with a marketplace-abstraction layer extended to others (**Vinted** live as of Stage 8, **Sbazar** shipped after it). It monitors search `Query` rows, detects new ads, filters them, and sends Discord notifications.

**The pipeline is decoupled into three independent processes that communicate through the `AdDelivery.status` column** (a queue in Postgres). `Ad` itself carries **no** pipeline state — migrations `0026`–`0028` moved it out — so every stage reads, locks and writes `AdDelivery`. Each stage polls with `select_for_update(skip_locked=True)` so multiple workers are safe:

```
run_scraper  →  ScrapeRunner (bazos/scraping/runner.py)               # orchestrates queries, IP rotation, sleep
                  → QueryRunner (query_runner.py)                     # per-query dedup, price-change detection
                    → MarketplaceScraper (BazosScraper)               # HTTP + BeautifulSoup; writes Ad + AdDelivery(PENDING)
run_filter   →  build_rule_engine(delivery.query) (bazos/filters.py)  # PENDING/PRICE_CHANGED → APPROVED / REJECTED
run_sender   →  DiscordSender (senders/services/)                     # APPROVED → SENT / FAILED (retry w/ backoff)
```

**Delivery status state machine** (`AdStatus` in `bazos/models.py`, stored on `AdDelivery.status`): `PENDING → APPROVED | REJECTED | SUPPRESSED`, then `APPROVED → SENT | FAILED`. `PRICE_CHANGED` re-enters at the filter stage. Each stage owns its transitions — the scraper must not send directly; it only sets `PENDING` (or `SUPPRESSED` for an `ignore_first_run` backfill). Batch sizes / poll intervals / `MAX_SEND_ATTEMPTS` live in `bazos/const.py`.

**Marketplace abstraction** (Stages 6–7):
- `bazos/scraping/marketplace.py` — `MarketplaceScraper` **Protocol** (`marketplace` attr, `run_query`, `load_full_description`, `check_blacklisted`). `BazosScraper` satisfies it structurally. Two things the signature doesn't tell you:
  - `check_blacklisted` is still a protocol member with four live implementations, but **nothing in production calls it** — the pre-flight probe was deleted (see the Blacklist/IP-guards pattern below) and only tests exercise it now.
  - `dedup_break_streak: int` is an **optional class attribute, deliberately not a protocol member** — `QueryRunner.run_existing_query` reads it via `getattr(..., 1)`. It says how many consecutive already-known, non-topped ads the dedup walk tolerates before stopping.
- `Marketplace` (`TextChoices` in `bazos/models.py`) is the single source of valid values — it types `Query.marketplace` *and* `Ad.marketplace` and keys the scraper registry. `BAZOS`, `BAZOS_API`, `VINTED` and `SBAZAR` are all registered and live.
- `_build_scrapers(session)` / `get_scraper(marketplace, session)` — **module-level** in `bazos/scraping/query_runner.py` (not a method). `QueryRunner.__init__` dispatches through `get_scraper`.
- `bazos/scraping/bazos/bazos_api_scraper.py` — `BazosApiScraper`, a second `MarketplaceScraper` using Bazos's hidden mobile JSON API instead of HTML (see `docs/research/bazos-api/HIDDEN_API.md`). Registered under `Marketplace.BAZOS_API` for validation only (`python manage.py compare_bazos_scrapers`) — no `Query` uses that value, so `run_scraper` stays HTML-only (`BazosScraper`) in production.
- `bazos/scraping/vinted/vinted_scraper.py` — `VintedScraper` (Stage 8), backed by the `vinted-scraper` PyPI package. Ignores the `session` it's passed — the library builds its own `httpx` client, since Vinted bans proxy/VPN traffic and Tor is a non-starter there. `Query.extra_params` (JSONField) carries marketplace-specific search params — Vinted reads `base_url` / `catalog_ids`, **Sbazar reads `base_url` / `category_id` from the same field**; both Bazos scrapers ignore it. See `docs/archive/shipped/VINTED_SCRAPER.md`.
- `bazos/protocols.py` — `Sendable` Protocol (`.message`, `.link`), replaces the old `SendableMixin` ABC. `Ad` implements it.

**Key models** (`bazos/models.py`):
- `Query` — what to scrape (text, price range, location, section/category, `marketplace`, `extra_params`, `sender` FK) **plus its filter config** (`filter_blocklist`, `filter_required`, `filter_rule_names`, `filter_location_center`/`filter_location_radius`) **plus per-query behaviour flags**: `enabled` (the pass only walks enabled rows), `load_full_description` (gates the extra detail GET per new ad), `ignore_first_run`, `randomly_generated` (force-disabled at the top of every pass). `new_query=True` triggers a backfill-only first run (up to `NEW_PRODUCT_LOAD_MAX=50`; suppressed if `ignore_first_run`).
- `Ad` — the **scraped facts** of one real-world listing, globally unique on `(marketplace, external_id)` (`external_id` was renamed from `bazos_id`). Carries `price_raw` (the display string, an audit trail), `price` (`BigIntegerField`, nullable — the parsed CZK amount) and `price_type` (a `PriceType` enum — `EXACT`, `NEGOTIABLE`, `IN_TEXT`, `MAKE_OFFER`, `INDIFFERENT`, `FREE`, `CURRENT_BID`, `UNKNOWN`: only `EXACT` and `FREE` carry a real `price`, the rest leave it null. `CURRENT_BID` is reserved for Aukro's live-bid semantics and no scraper sets it yet; `UNKNOWN` means a marketplace started using a price string the parser doesn't know), plus optional FKs to `EmailPublisher` / `PhonePublisher`. **It carries no pipeline state and no `query` FK** — both moved to `AdDelivery` in migrations `0026`–`0028`.
- `AdDelivery` — **one query's interest in one ad, and the delivery state machine for it** (`ad`, `query`, `status`, `filter_reason`, `sent_at`, `send_attempts`). Delivery is a property of `(ad, query, sender)`: the same listing matching two queries must notify both channels, which is why it can't live on `Ad`. Every pipeline stage reads and locks *this* table, not `Ad`; filter rules take an `AdDelivery`.
- `PriceChange` — append-only price history (`ad.price_history`), carrying both the display strings (`old_price`/`new_price`) and the parsed amounts (`old_price_amount`/`new_price_amount`). Written by `QueryRunner.run_existing_query` when a re-seen ad's `price_raw` differs; it also flips **every delivery of that ad** to `PRICE_CHANGED`, which is the *only* producer of that status. `PriceDropRule` reads the newest row back.
- `PostalCode` — **PSČ → coordinates, cached from Bazos's `zip.php` geocoder** (`bazos/geo.py`), read by `location_distance`. A cache, not a reference table: rows appear as the scraper meets new codes — `QueryRunner._resolve_ad` calls `ensure_postal_code` right after saving a new `Ad`, and `ScrapeRunner._ensure_filter_centres` does the same once per pass for every enabled query's `filter_location_center`, which has no creation moment of its own because it is typed into the admin. So a miss means "not looked up yet", never "nowhere". It is a table rather than a bundled JSON artifact like `bazos/pricing/artifacts/` because the CZ code list cannot be obtained offline — `zip.php` caps a prefix search at ~9 rows, so there is nothing to enumerate from. Coordinates are the **post office's**, not the seller's, which puts a few-km floor under any distance measured from them.
- `QueryChange` — **append-only audit of `Query` configuration edits** (`query`, `query_label`, `changes`, `created`), `related_name="config_history"`. `changes` is a field-level diff, `{field: {old, new}}`, not a snapshot — past state is reconstructed by replaying diffs backwards from the live row. Written by `Query.save()` when the diff against `TRACKED_CONFIG_FIELDS` is non-empty; old values come from a deep copy taken in `Query.from_db`, so the `query.save()` that fires once per query per pass costs no extra SELECT. Three things are deliberate: `new_query` and `randomly_generated` are **not** tracked (both are pipeline-managed — tracking the first would write a row per query per pass); `Query.objects.filter(...).update(...)` bypasses `save()` and is **invisible** to the log (the one in production touches no tracked field); and the FK is `SET_NULL` with a `query_label` string snapshot, so "what did this query look like before I deleted it" still answers.
- `AdPriceScore` — **what a price model thinks one ad is worth** (`predicted`, `residual_log`, `discount_pct`, `z_score`, `features`, `model_name`/`model_version`), unique on `(ad, model_name)`. The numbers stay typed columns because they are what an admin changelist sorts and filters by; `features` is JSON because the feature set is the *model's* vocabulary, not this table's, and it is what answers "why did it think this was cheap" — extraction, not model class, is the measured weak point (`docs/research/PRICE_MODEL_BENCHMARK.md` §3.1). A child table of `Ad` for the same reason `PriceChange` is one — `Ad` is re-read every pass and rendered on a changelist already tuned for cost. It hangs off `Ad`, **not `AdDelivery`**, because what a listing is worth doesn't vary by query; whether that's cheap enough to *notify* about is the per-query decision and lives in the filter. A declined score is still written (null numbers + `declined_reason`): "a model looked and had no opinion" is a different fact from "nothing looked". `features` is also what **`bazos/comparables.py`** buckets on — see below.

**Comparables** (`bazos/comparables.py`): "where does this ad sit among listings of the same thing". The hard part is deciding what *the same thing* is, and this borrows that answer rather than inventing one: it reads the spec bucket off the subject's persisted `AdPriceScore.features`, using the `comparable_keys` the claiming model declares. That is an **optional class attribute, not a `PriceModel` protocol member** — the same call as `dedup_break_streak` on the scraper protocol; a model that predicts prices need not also have an opinion on comparability, and one that doesn't simply yields no comparables. Three consequences: coverage equals *scoring* coverage, so the comparables line and the model line appear together or not at all; a bucket with any null in it **declines** rather than matching every ad missing that same spec; and counts are of **listings, not units** — relisting is not deduplicated, and 56% of the MacBook corpus comes from ten dealers. `Ad.current_price_score()` caches the score per instance so both notification lines cost one lookup between them, and an unscored ad short-circuits before the comparables query ever runs.
- `QueryRun` — per-execution metrics; always saved, including on failure (`success`, `error`, `exit_ip`). **One row per *attempt***, not per query per pass: a blacklisted query is retried on a fresh IP, so it leaves up to `MAX_BLACKLIST_RETRIES` rows. `exit_ip` is the egress the **marketplace itself named** in its 403 body, and is populated on block rows only — a successful run leaves it empty because no lookup can answer for the circuit it travelled (see IP rotation below). Group blocks by it; do not read a blank as "unknown IP on a run that worked". `Section` / `Category` — Bazos taxonomy + URL helpers.
- `EmailPublisher` / `PhonePublisher` — opaque Bazos seller ids with a `blocked` flag; share `PublisherMixin.partner_rows()` ("who else appears alongside me").
- `Discord` (`senders/models.py`) — webhook configs (`notify` ping flag, `for_logging` flag, `for_summary` flag — see the end-of-pass digest below).

**Filtering** (`bazos/filters.py`): `run_filter` builds a per-delivery engine via `build_rule_engine(delivery.query)`. Rules take an `AdDelivery`, run in order, **first non-`PASS` wins**, all-`PASS` ⇒ approve. Shipped rules (`RULE_REGISTRY`):

| rule name | rejects when | stays neutral (`PASS`) when |
|---|---|---|
| `price_range` | `ad.price` outside `query.price_lower..price_upper` | range is `0-0` ("no filter"), or `ad.price is None` (a placeholder `price_type` — `Dohodou`, `V textu`). Note `FREE` is **not** exempt: it carries a real `price=0`, so a free ad is rejected whenever `price_lower > 0` |
| `blocklist_keyword` | `name`+`short_description` contains a `query.filter_blocklist` phrase | list empty |
| `required_keyword` | `name`+`short_description` contains none of `query.filter_required` | list empty |
| `publisher_blocklist` | the ad's email/phone publisher has `blocked=True` | neither is blocked |
| `price_drop` | a `PRICE_CHANGED` ad whose newest `PriceChange` did **not** go down | ad isn't `PRICE_CHANGED`, or no parseable history |
| `location_distance` | the ad's postal code is further than `query.filter_location_radius` km from `query.filter_location_center` | **both fields blank (the default)**, the ad's `location` carries no postal code (every Sbazar/Vinted ad), or either code is missing from the `PostalCode` cache |
| `price_model` | a price model scores the ad and it is **not** a deal — inverted vs every other rule, which is what makes a dedicated alert query work. Thresholds resolve **per query → settings → `const`** (`Query.filter_price_model_z` / `filter_price_model_min_discount`, both nullable so "untuned" stays distinct from "tuned to the default") | shadow mode is on (**the default**), no model claims the ad, or the model declined (missing artifact, incomplete specs, damage words, non-EXACT price) |

`Query.filter_rule_names` selects which rules apply — **empty means all of them** (the same permissive-when-empty convention as the two keyword lists); an unknown name raises `ValueError` when the engine is built. `PassthroughRule` is a test-only no-op and is *not* wired into `run_filter`.

**Admin theme** (`django-unfold`, configured in `settings.UNFOLD`): Unfold *replaces* `django.contrib.admin`'s templates rather than extending them, which has three consequences worth knowing before touching the admin.
- **`INSTALLED_APPS` order is load-bearing.** `unfold`, `unfold.contrib.filters` and `unfold.contrib.forms` sit above `django.contrib.admin`; move them below it and template lookup silently returns to the stock admin.
- **A new `ModelAdmin` must subclass `unfold.admin.ModelAdmin`** (and inlines `unfold.admin.TabularInline`). A stock one still *works* — the chrome comes from the templates — but its widgets and filters stay unthemed, and `test_every_registered_changelist_renders` will not catch that, because the page is still a 200. This is also why `django-db-logger`'s `StatusLog` is unregistered and re-registered on the themed base at the bottom of `bazos/admin.py`. Widgets declared by hand on a form are the same trap: `QueryAdminForm.filter_rule_names` names `UnfoldAdminCheckboxSelectMultipleWidget` explicitly, since only model-derived fields get mapped automatically.
- **The sidebar is hand-maintained.** `UNFOLD["SIDEBAR"]["navigation"]` is grouped by pipeline stage rather than by Django app, because `Query`/`Ad`/`AdDelivery` all live in `bazos` but belong to different jobs. A newly registered model does **not** appear there on its own — it only shows up under "All applications" until a row is added.

Filters that take two inputs (`RangeNumericFilter` on `Ad.price`, `RangeDateTimeFilter` on the `created`/`run_start` columns) need `list_filter_submit = True` on the admin, or the sheet renders them with nothing to apply them.

**Price scoring** (`bazos/pricing/`, spec: [`docs/proposals/ML_PRICE_SCORING.md`](docs/proposals/ML_PRICE_SCORING.md)): a `PriceModel` Protocol + `MODEL_REGISTRY` (the third instance of the Protocol-plus-registry pattern, after `MarketplaceScraper` and `RULE_REGISTRY`). `get_price_model(ad)` returns the first model whose `applies_to` claims the ad; `score_ad()` persists the result as an `AdPriceScore`. `price_model` is registered but **deliberately excluded from `DEFAULT_RULE_NAMES`** — it REJECTs anything it doesn't consider a deal, so enabling it by default would mute every existing query. Two things to know before touching it:
- **Artifacts are JSON, not pickles, and that is a hard constraint rather than a preference.** There is no numpy/scipy/scikit-learn in the *runtime* dependencies, and adding them to an ARM64 Pi image to evaluate a few dozen coefficients isn't worth it. `bazos/pricing/artifacts/<name>/<version>/manifest.json` carries the feature spec and coefficients as plain numbers; inference is a dot product in pure Python. sklearn is needed only to *train* (`manage.py train_price_model`), and is not in `pyproject.toml` at all — install it in a dev env. An artifact with `kind` other than `linear` is refused on load.
- **Every uncertain path is neutral, never rejecting.** A missing/corrupt artifact, an unknown feature kind, a failed gate, or an exception during scoring all end in `PASS`. A model that cannot score must not be able to silently drop every ad on a query that enabled it.
- **Precision is not measurable yet.** `Ad.modified` never advances past `created`, so the DB records no outcomes — no time-to-disappear, no sold flag. Every quality figure available is a *composition* audit, not a measurement, which is why `PRICE_MODEL_SHADOW_MODE` defaults to `True` and why P24 gates calibrating any threshold here.

**Seller identity** (`SellerAdCounts` in `bazos/models.py`): a Bazos seller is a *pair* of opaque ids (email_id, phone_id) and the same person routinely posts under many pairings, so counts are reported three ways — `by_email`, `by_phone`, `combined` — and their disagreement is the signal. `combined` walks the email↔phone graph transitively to a fixpoint, bounded by `MAX_IDENTITY_ROUNDS=5`. Two consequences worth knowing before touching it: counts are of ads **in this DB**, not the seller's true Bazos total; and `Ad.message` embeds `seller_ad_counts().summary`, so rendering an ad for Discord fires several `COUNT` queries — never call `.message` in a loop over a large queryset. Migration 0025 removed a `bazos_id=0` sentinel that used to merge unrelated sellers into one identity.

**Senders** (`senders/services/`): `Sender` ABC + `DiscordSender` (the only production sender; posts via `discord_notify`, raises `RateLimitError` on HTTP error for the sender's retry loop, retries `URLError` in-process up to `MAX_CONNECTION_RETRIES`). `SlackSender`, `EmailSender`, `CalendarConditionSender` are experimental stubs — some import broken `src.*` paths and won't run.

**Two links per ad message.** `DiscordSender._format_product_message` appends `Ad.admin_url` — an absolute link to the admin change page, `SITE_BASE_URL` + `reverse()` — under the marketplace URL. Three things are deliberate: it is read with `getattr` and is **not** a `Sendable` protocol member (same call as `dedup_break_streak` — being sendable shouldn't imply having a row in *this* admin); it is **always** wrapped in `<>` regardless of `preview_link`, because `SITE_BASE_URL` names a host only we can reach and Discord's crawler would just render a failed embed; and it is keyed on `pk`, so links already sent do not survive a DB rebuilt from a dump with different sequence values. `SITE_BASE_URL` must be configuration rather than inferred — `run_sender` serves no HTTP request, so there is no `Host` header, and an `.local` name resolves on the LAN only (a link built from one is dead on mobile data, which is exactly when the notification matters). `test_pipeline_e2e.py` pins it and normalises the pk out of its golden messages, which would otherwise encode whichever hostname the developer's `.env` happened to hold. Serving a *public* ad page was considered and deferred — [`docs/proposals/PUBLIC_AD_PAGES.md`](docs/proposals/PUBLIC_AD_PAGES.md).

**End-of-pass digest** (`bazos/scraping/pass_summary.py`): after every pass `ScrapeRunner._send_pass_summary` posts one message to each `Discord` row flagged **`for_summary`** — per-query new-ad counts grouped by marketplace, failures first, queries that found nothing collapsed into a `+ N queries, no new ads` tail. Four things are deliberate:
- The counts are **discovered, not notified**. The filter is a separate process polling `PENDING`, so nothing in the pass is APPROVED or REJECTED yet; a query can discover 12 and have all 12 rejected seconds later. Never label this column "sent".
- Summary senders are built with **`notify=False` whatever the row's `notify` says** — the digest fires every 15–45 minutes, and an `@here` that often is how a channel gets muted, taking the canary alerts with it if it shares one. Keep `for_summary` off the `for_logging` channel for the same reason.
- A **quiet pass renders as one line**, not a table of zeroes. Same reason.
- `_send_pass_summary` has its **own** try/except rather than relying on the pass-level guard in `run()`: a `RateLimitError` from the webhook would otherwise be announced as `Pass FAILED` for a pass that scraped fine. Message length is capped at `MAX_MESSAGE_CHARS=1900` (Discord hard-rejects over 2000) and trimmed rows are counted, since the formatter is the one thing here that grows with the query count.

`ScrapeRunner._run_query_with_rotation` returns a `QueryResult` (never `None`) so failures reach the digest — the canary still counts only successful queries, which is the same arithmetic as before.

**Django admin** (`bazos/admin.py`, ~810 lines — a real operational surface, not scaffolding): force-run button (an Unfold `actions_list` action, still served at `force-run/`, see below), per-query ad count + last-run annotations, `filter_rule_names` rendered as checkboxes and `extra_params`/blocklist JSON validated in `QueryAdminForm.clean_*`, publisher partner tables with block/unblock actions and links into a filtered `Ad` changelist, `AdDelivery` and `PriceChange` inlines on `Ad`, a capped `QueryChangeInline` on `Query` (a change form renders every inline row — there is no pagination — so it shows the newest `MAX_ROWS=15` and links out to the filtered changelist), standalone read-only `AdDeliveryAdmin` and `QueryChangeAdmin`, and a `HasFullDescriptionFilter` on the `Ad` changelist. The Query changelist is ordered `("-enabled", "marketplace", "text")` — stable across passes on purpose (a control panel that reshuffles every 15–45 minutes is unusable), and `-enabled` is what sinks the `randomly_generated` rows, since the runner force-disables them at the top of every pass. Its `last_run` column sorts by `F("last_run").desc(nulls_last=True)` rather than the bare field name: `last_run` is a `Subquery` that is NULL for a never-run query and Postgres's DESC is NULLS FIRST, so "most recently run" would otherwise open on the queries that have never run — the same trap as `AdAdmin.ordering`. `QueryAdmin.get_queryset` computes `ad_count`/`last_run` as **correlated subqueries, never `annotate(Count('deliveries'), Max('runs__...'))`** — two aggregates over two reverse FKs join both tables into one query and Postgres materialises a deliveries × runs product per row, which is what made the changelist slow as history grew. `test_admin.py::test_changelist_queryset_does_not_join_deliveries_or_runs` guards it. Note that `QueryAdmin` now carries an inline, so any programmatic POST to the Query change form must include the `config_history-*` management form — without it the formset is invalid and the view re-renders as **200 with an empty `form.errors`**, which reads exactly like a silent no-op (see `valid_query_data` in `test_admin.py`).

**IP rotation** (`ip_changer/`): `IPChanger` ABC (`ip_changer.py`) with `TorIPChanger` (`tor.py`) and `DummyIPChanger` (`dummy.py`, no-op for dev), selected by `IP_CHANGER_TYPE`. `OpenVPNIPChanger` (`openvpn.py`) is an unfinished stub. The one method that matters is `rotate_circuit() -> bool`: it moves the changer's session onto a different egress and reports whether the transport *has* another one (Tor: always; Dummy: never, so the runner stops retrying instead of re-running a query against the one IP it has). It never validates the new egress against the marketplace — that is the caller's next real query attempt.

**Rotation is a fresh SOCKS credential, not a NEWNYM signal**, and the reason is the single most load-bearing fact about this transport: **the Tor container runs `SocksPort ... IsolateDestAddr`** (`dperson/torproxy`'s default), so **every destination host gets its own circuit with its own exit node**. Measured live 2026-08-29 from one `requests.Session`, seconds apart: `icanhazip.com` → `171.25.193.38`, `pc.bazos.cz` → `37.114.63.5`, `nabytek.bazos.cz` → `193.189.100.201`. Consequences:
- **Reading icanhazip cannot tell you what a marketplace sees.** `get_current_ip` answers for the icanhazip circuit only. `check_ip_local` is the one caller that question is still right for — "is *any* traffic leaving unproxied" is a property of the transport, not of one destination. The block response is the only trustworthy source for the marketplace's view, and it gives it away for free: both body formats end `... permission to access this server. IP: x.x.x.x` (nginx HTML on the site, the same sentence inside `{"error_code":"403","message":...}` on the API). `MarketplaceBlockedError.from_response` parses it; `QueryRun.exit_ip` stores it. The IP is deliberately kept **out** of the exception message, because `QueryRun.error` is `f"{type(e).__name__}: {e}"` and an IP there would shatter one failure mode into hundreds of one-row groups.
- **A fresh SOCKS username is a fresh circuit** (`IsolateSOCKSAuth`, on by default), built on demand in **0.6-1.2 s**, no control-port round trip and no rate-limit wait. That is `rotate_circuit`: swap `circuit_id`, rebuild the session. The NEWNYM loop it replaced cost 10-50 s per retry (signal → 10 s sleep → re-read icanhazip, up to `MAX_RENEW_ATTEMPTS` rounds under a `ROTATION_DEADLINE_SECONDS` wall clock) to verify a circuit nobody was going to use.
- **Around half of all Tor exits are 403'd by Bazos** — 5/12 and 8/14 in two probes on 2026-08-29, ~48 % implied by the QueryRun history — independent per destination host, so every attempt is an independent ~coin flip. That is what sizes `MAX_BLACKLIST_RETRIES=8` — at 3 it lost ~14 % of query-passes outright, which is exactly what the history shows (1428/1654 = 86.3 % eventual success, 2026-08-24..29); 8 puts the expected loss near 1 % across that whole spread. Don't read the number as timidity about load: eight ~1 s rotations are cheaper in wall clock *and* in requests-that-achieve-nothing than three that each cost a NEWNYM round trip and then give up.

`TorIPChanger.renew_ip()` (NEWNYM via the Stem control port on 9051) survives as the coarse manual reset — nothing calls it. Don't read its existence as evidence the retry path signals the control port.

**LLM layer** (`llm/`, design: [`docs/proposals/PRICE_REFERENCE_SERVICE.md`](docs/proposals/PRICE_REFERENCE_SERVICE.md) §2): an `LLMProvider` Protocol + `PROVIDER_REGISTRY` — the **fourth** instance of the Protocol-plus-registry pattern, after `MarketplaceScraper`, `RULE_REGISTRY` and `MODEL_REGISTRY`. `llm.services.complete()` is the entire public surface. **Nothing in the pipeline calls it yet.** Five things to know before touching it:
- **`LLM_PROVIDER` defaults to `NULL`** — a real provider that declines every call and opens no socket. This is `DummyIPChanger`'s role: the suite and a fresh checkout run with no API key and no egress, so every caller's decline path is exercised in CI rather than only in production. Two networked providers, both over `requests` and **not the vendor SDK** — the same call `bazos/pricing` makes evaluating a linear model with a dot product instead of putting numpy on an ARM64 Pi image.
- **`GEMINI` is the one to reach for, and the reason is measured.** `LLM_AD_REVIEW.md` §2f found a free tier of ~1,500 requests/day — above a filtered candidate stream — and that under Google's terms the **paid-tier data terms apply to the free tier for EEA/UK/CH users**, so free-tier prompts are not used for training. Those terms also say not to send personal information to the unpaid services; public listing text is fine and `refprice` sends nothing else. Two things differ from the Anthropic path: **`responseSchema` constrains the output server-side** (the dataclass is translated into the API's schema language, so `parse_into` is a formality rather than a gamble — the single biggest reliability difference between the two), and **429 is expected steady state on a free tier**, so the retry budget is longer and honours Google's `RetryInfo.retryDelay`.
- **`LLM_MODEL` is blank by default and each provider carries its own `DEFAULT_MODEL`.** A single shared default would be one provider's model name handed to another — a 404 that looks exactly like a broken key. Gemini's default is `gemini-3.5-flash-lite`, pinned rather than `…-latest`: a model that changes underneath makes a stored result unattributable, the same reason prompts are versioned files. **A model being listed is not proof it is callable** — `gemini-2.5-flash-lite` appears in the models endpoint and 404s on `generateContent` (measured 2026-09-16). `manage.py llm_check` makes one real call and reports tokens/cost/latency; `--models` lists what the key can reach.
- **An unpriced model records cost 0 and warns once.** Correct on a free tier, and wrong on a paid key — `LLM_MONTHLY_BUDGET_USD` cannot protect spend it is never told about, so add the model to that provider's `PRICING` before pointing a paid key at it.
- **Declining is never an exception.** A refusal, unparseable JSON, a raising provider, a truncated answer or an exhausted budget all return an `LLMResult` with `value=None` and a `declined_reason`. Same rule as `PriceModel.predict` and `bazos/pricing`'s "every uncertain path is neutral".
- **Every call writes an `LLMCall` row**, success, decline and error alike — `QueryRun`'s rule. Cost and prompt-version attribution are only ever asked in arrears.
- **`LLM_MONTHLY_BUDGET_USD` declines *before* calling out**, not after. A ceiling that reports overspend afterwards is not a ceiling, and this is the one failure mode here that costs real money. `0` disables LLM calls entirely.
- **Prompts are versioned files** (`llm/prompts/<name>/v<N>.md`), same discipline as `bazos/pricing/artifacts/`: editing a shipped prompt in place is a bug, adding `v2` is the change. Substitution is `$name`, not `str.format`, because the templates are full of JSON examples. The response cache keys on provider, model, prompt name **and version**, the prompt text **and the schema** — the cached object is an instance of that schema, so omitting it hands back the wrong type. Declines are not cached.
- **No network I/O inside `run_filter`.** `complete()` must never be called from a filter rule: `run_filter` holds `select_for_update` locks while rules run. This is why reference-price lookup is explicit-only.

**Reference prices** (`refprice/`, design: [`docs/proposals/PRICE_REFERENCE_SERVICE.md`](docs/proposals/PRICE_REFERENCE_SERVICE.md), measured: [`docs/research/marketplaces/ZBOZI_API.md`](docs/research/marketplaces/ZBOZI_API.md)): what a listing costs *new*, and what it has cost over ~2 years, from Zboží.cz. `refprice.services.lookup_reference_price()` is the entire public surface — plain dataclasses in and out, no `Ad` crossing the boundary, so it stays extractable into a service. Run it from the **Ad admin action** or `manage.py lookup_reference_price --ad N | --query N | --refresh-stale`.
- **It is explicit-only, and that is a feature.** Nothing in `run_scraper`/`run_filter`/`run_sender` calls it — it does network I/O, and `run_filter` holds `select_for_update` locks while rules run. Every admin confirmation writes `RefProductLink.confirmed_by_human`, which is a labelled `(ad title → product id)` pair; that corpus is what would later justify automating any of this, and a fully automatic v1 would produce none of it.
- **Never returns a bare number.** The measured failure modes are *confident and wrong* — a 2020 MacBook baselined at 47 370 Kč from a 2025 M5, a Dell XPS at 262 Kč from a laptop bag. `ReferenceResult` carries six statuses plus every candidate considered and why it was rejected. **`NO_MARKET` is not `NO_MATCH`**: the first means the product exists but has ≤1 merchant, which is information *about the ad* (it is old), not an absence of information.
- **`medianPrice`, never `min`.** Zboží's name-based pairing puts a different product's cheaper offer at the bottom of the range (a 484 Kč accessory in the Makita series), and it poisons min, not median. Prices arrive as **hundredths of CZK** under two spellings (`minPrice`, `minPriceHa`) and are converted exactly once, at the provider edge — `parse_price` strips non-digits, so an unconverted value lands 100× too large.
- **The ladder is rungs 0–5 and every rung can decline**: cache → rule normalisation → suggest + validate → LLM phrase → LLM adjudication → the robots-disallowed `?q=` search. Rungs 3–4 need `use_llm` **and** a configured provider; rung 5 needs `allow_disallowed_search=True` per call and stamps `robots_allowed_path=False` on the result. Rungs 0–2 are the whole usable feature and cost nothing.
- **Validation runs over every candidate, never rank 0** — top-1 was wrong or empty in 8 of 17 live archetypes while the right answer sat further down. Three traps are encoded as regression tests: a model code is the identity and the seller's Czech prose is optional; the phrase **truncates at the model code** (`Makita DHP484Z 18V` suggested Merrell shoes — a voltage is a spec, not an identity); and a prefix match needs ≥3 characters (`Kärcher K5` matched a **K4** on the `K`).
- **`reference_price` is registered but excluded from `DEFAULT_RULE_NAMES`**, exactly as `price_model` is, and reads *only* persisted `RefProductLink` rows — it must never call Zboží. Register a rule from another app with `bazos.filters.register_rule(rule, opt_in=True)` at `AppConfig.ready()`; assigning into `RULE_REGISTRY` directly leaves `DEFAULT_RULE_NAMES` decided by import order. **`bazos` imports nothing from `refprice`** — both the admin wiring and the rule registration happen on this side, and tests assert it.
- **Do not route it through Tor.** Zboží does not block, and CZ sites 403 Tor exits widely; the provider builds its own session, the same call `VintedScraper` makes. It is an **unsupported private API** — `refprice/tests/test_zbozi_contract.py` is the weekly drift check, picked up by `contract-check.yml`'s `-m live` glob.

**Other apps:**
- `facebook/` — `FBUser` model + `python manage.py import_data --path <file>` to bulk-load a leaked FB dataset; joined to ads via `PhonePublisher.fb_user` for publisher enrichment.
- `getyourguide/` — a **standalone script** (`gyg_scraper.py`), not in `INSTALLED_APPS`; polls a GetYourGuide tour API and fires a Discord webhook when a spot opens. **It is untracked and not gitignored** — it exists in the working tree but was never committed, so a fresh clone does not have it. Commit it or stop treating it as part of the repo.

**Observability:** app loggers (`bazos`, `senders`, `ip_changer`) log at INFO to console **and** the DB via `django-db-logger`. Sentry is enabled only when `SENTRY_DSN` is set *and* not under pytest (error tracking, no perf tracing). **`SENTRY_ENVIRONMENT` defaults to `development`, not `production`** — the SDK's own default is "production" when unset, which made every developer machine holding a `SENTRY_DSN` report as the Pi (six of ten issues in one 24h window were `manage.py shell` sessions against a dev database). The *only* thing that marks a run production is `deploy.yml`'s "Stamp the release" step, which writes `SENTRY_ENVIRONMENT` and `SENTRY_RELEASE=<tag>` into the Pi's `.env` — written to the file rather than exported for the job so it survives a manual `docker compose up` or a reboot, and written before `down` so the recreated containers pick it up through `env_file`. `bazos/tests/test_sentry_config.py` guards both halves, because deleting either one relabels events silently instead of failing.

**Existing-query dedup**: `QueryRunner.run_existing_query` walks newest→oldest and stops after `scraper.dedup_break_streak` **consecutive** already-known, non-TOP ads. "Known" means *this query* already has an `AdDelivery` for the listing — not that the `Ad` row exists, which it may well do for a different query. The default of 1 (Bazos, Vinted — neither overrides it) is only safe because those sites order by creation time, so everything below the first known ad is provably older. `SbazarScraper` sets `SBAZAR_DEDUP_BREAK_STREAK=40`: Sbazar's default order is `sorting_date` (~= edit time), so an old known ad resurfaces above genuinely new ones just for being edited. Either way the walk stays bounded by the scraper's own max-pages net.

**Force-run**: `ScrapeRunner._interruptible_sleep` wakes early (within ~5s) when `force_run.flag` (`settings.FORCE_RUN_FLAG_PATH`) appears, so the admin button can interrupt the sleep between passes.

**Testing:** the suite runs on **real Postgres**, the same engine as production, so Postgres-only behaviour is genuinely exercised — `select_for_update(skip_locked=True, of=("self",))` reaches the SQL, migration 0027's deferred-FK-trigger flush executes, and `max_length`/`int4` limits are enforced (all three are silently no-ops or unenforced on SQLite). Locally that means **`docker compose up -d postgres` must be running**; connection settings come from `.env` (`POSTGRES_HOST=localhost`, port 5435) and Django builds an isolated `test_<POSTGRES_DB>`, never touching the dev database. CI (`test.yml`) provides a `postgres:15.2` service container.

The root `conftest.py` hooks `django_db_modify_db_settings` (not `django_db_setup`) so that `TEST_DB=sqlite` can swap in SQLite `:memory:` — used by **one** caller, `contract-check.yml`'s live job, which runs in a container with no DB and only asserts on live-site parsing — while leaving pytest-django's own `--reuse-db`/`--create-db` intact. A test that passes on SQLite and fails on Postgres is reporting a real defect; don't reach for the env var to silence it. Measured 2026-08-24 on **629 tests** (635 collected, 6 `live` deselected): Postgres ~41 s reusing the database, ~46 s building it fresh, ~65 s under `--create-db` (which drops an existing one first); SQLite runs the same 629 in ~35 s. **`--reuse-db` no longer halves anything** — it saves roughly 5 s. The suite has grown enough that test *execution*, not the ~38-migration chain, now dominates the run, so the flag is no longer the win it was. Re-measured 2026-09-15 on the Django 5.2 / Python 3.12 stack: **853 tests** (859 collected, 6 `live` deselected) in ~47 s on Postgres, so the shape of that conclusion is unchanged. Caveat — the migration tests roll the schema backwards and forward again in a fixture teardown, so a run killed mid-test can strand a reused DB at an older schema; `--create-db` rebuilds it, and the default (no flag) is immune. `conftest.py` also no-ops `DatabaseLogHandler.emit` session-wide so DB-free unit tests can log.

Note `POSTGRES_HOST` in `.env` is the **host-side** value (`localhost`). The compose services don't read it — `docker-compose.yml` pins `POSTGRES_HOST: postgres` in each service's `environment:` block, which overrides `env_file`. Before that pin, `.env` had to say `postgres` and nothing on the host could connect at all.

## Coding patterns

- **Pipeline stages own their `AdDelivery.status` transitions.** New long-running stages should poll with `select_for_update(skip_locked=True, of=("self",))` and a status filter, like `run_filter`/`run_sender`. The `of=("self",)` matters — both commands `select_related`, and without it the joined `Query`/publisher rows get locked too.
- **Adding a marketplace**: add a `Marketplace` choice, implement the `MarketplaceScraper` protocol, register it in `_build_scrapers()`; don't special-case it in the runner. The two shipped examples are written up field-by-field in `docs/archive/shipped/VINTED_SCRAPER.md` (Vinted) and `docs/archive/shipped/SBAZAR_SCRAPER.md` (Sbazar) — read the traps sections before touching either scraper, and `docs/research/PRICE_PARSING.md` §2 before writing any `_format_price` (the four marketplaces encode price three different ways, and "zero" three different ways).
- **The User-Agent pool is desktop-only, and that is load-bearing.** `ip_changer/tor.py` imports `requests_random_user_agent` for its side effect (it patches `requests.utils.default_user_agent` to draw from a pool **per call**), then immediately strips every phone/tablet agent via `drop_mobile_user_agents()`. **Bazos serves a different DOM to mobile User-Agents** — measured 2026-09-17, same circuit, seconds apart: desktop got 20 parseable rows, iPhone and Android each got 20 rows with **no `inzeratycena` at all**. The mobile markup puts price and locality inline in `div.popis` and has no `inzeratycena`/`inzeratylok`/`inzeratyview`/`inzeratyakce`, so `_parse_product` raises `AttributeError` on the first row and takes the whole page with it (`run_query` does `list(get_page_products(...))`). That lands **outside** `_tolerating_one_bad_ad` — it fires while the generator is being iterated, not in the loop body — and is not a `MarketplaceBlockedError`, so there is no retry and the query is written off for the pass. 2 of 62 agents were mobile, i.e. ~3% of sessions. Do **not** "fix" this by teaching the parser the mobile layout: it has no `inzeratyakce`, the only source of `publisher_email`/`publisher_phone`, so parsing it would silently drop seller identity.
- **Blacklist / IP guards**: there is **no pre-flight blacklist probe** — the query attempt *is* the probe. `ScrapeRunner._run_query_with_rotation` catches `MarketplaceBlockedError` from the real request, rotates the circuit (`change_ip` → `rotate_circuit`, no validation), and retries the same query up to `MAX_BLACKLIST_RETRIES`; any other exception is not retried. Don't reintroduce a probe: the old one hit a single fixed `search.php` URL and reported "clear" while the query's own page 403'd (2026-08-23 QueryRun history — every failure row had just passed it), and it cost a full search request per query. Under `IsolateDestAddr` it *could not* have been right — the probe URL and the query URL are served by different circuits with different exit IPs, so it was answering about an egress the query would never use. `check_ip_local()` runs **once per pass**, skipping the pass (never the sleep). When editing that loop, make sure every path either advances the loop or sleeps, or you get a hot request loop. The scrapers' own `check_blacklisted()` survives as a protocol member but is now called only by tests — don't read its existence as evidence a probe is still wired in.
- **One bad listing must not wedge a query.** `QueryRunner._tolerating_one_bad_ad` catches `DatabaseError` around each listing's writes, so an unusable row is skipped instead of aborting the walk — which, since the marketplace keeps serving that row, meant aborting on every pass indefinitely (a `varchar(300)` overflow wedged one query for two hours on 2026-08-23). **`DatabaseError` and nothing wider**: a bare `except Exception` swallowed `requests.ConnectionError` escaping `load_full_description`, so a dead detail-fetch transport finished the walk with `success=True` and zero new ads and was misread as a quiet market. `MarketplaceBlockedError` is not a `DatabaseError`, so it propagates on its own. There is **no `transaction.atomic()`** in the guard on purpose — the walk is autocommit so there is nothing to roll back to, and wrapping it opened a real transaction (not a savepoint) held open across the Tor detail fetch, pinning the new Ad's row and index locks. Wrapping the walk in `atomic()` later means adding a savepoint *and* hoisting the network fetch out of the guard; the two go together.
- **Scraped text fields have no real `max_length`.** `Ad.short_description` is a `TextField` because `CharField(300)` overflowed on a live Bazos listing and `DataError` aborted the walk. Widen rather than truncate: the keyword rules match `name + short_description`, so a cut tail silently stops blocklist/required phrases matching. `name` (120), `location` (128) and `publisher_name` (100) are the same latent class — the per-ad guard is what stops the next one being an outage.
- **A broken transport must not kill the daemon.** `ScrapeRunner.run` guards each pass. `run_scraper` does restart a crashed runner, but that rebuilds `ScrapeRunner` and so resets `zero_rows_passes`/`zero_new_ads_passes` — meaning a genuine parser-drift streak could never reach its alert threshold if a crash landed mid-streak. A failed `check_ip_local` lands here too and skipping is the right answer: if we cannot see our own egress, the transport is down. `--unsafe` is plumbed through as `ScrapeRunner(unsafe=True)` so crash-fast mode still crashes.
- **Distance filtering resolves in the scraper, measures in the filter.** `location_distance` needs coordinates, and the split is deliberate: `bazos/geo.py::ensure_postal_code` (the only thing that talks to `zip.php`) is called from `QueryRunner._resolve_ad`, where a Tor session, pacing and block handling already exist and where it runs *before* the `AdDelivery` row exists — so `run_filter` stays network-free and cannot race a half-warm cache. `distance_between_codes` is pure arithmetic over `PostalCode`. Don't move the lookup into the filter to close the gap for ads scraped before the feature; `manage.py geocode_postal_codes` is what closes that. `geocode_postal_code` catches `Exception`, not just `requests.RequestException`, because its caller sits inside the walk guarded only for `DatabaseError` — an escaping geocode error would cost a real ad.
- **Pacing**: bursts, not steady volume, are what correlates with 403s. Every Bazos request path is paced — `BAZOS_PAGE_WAIT_TIME` between listing pages, `BAZOS_DETAIL_WAIT_TIME` inside `load_full_description` (called once per new ad with no delay in the caller), `QUERY_WAIT_TIME` between queries in a pass (unprefixed because `ScrapeRunner` applies it to every marketplace). Vinted pays this only on the detail path — `VINTED_DETAIL_WAIT_TIME`, because a `new_query` backfill fires up to `NEW_PRODUCT_LOAD_MAX` unpaced `item()` calls in a row; its search is measured clean. A new scraper's `load_full_description` must pace itself; the runner will not do it.
- **Every request needs a timeout, and the retry budgets nest.** `BAZOS_REQUEST_TIMEOUT=(20, 30)` connect/read on every Bazos call — through Tor an unreachable host is a *stalled socket*, not a refused connection, so without it a single hung GET stalls the pass with nothing to interrupt it, and the connect half must cover circuit construction. `run_request` retries `MAX_ATTEMPTS=5` times and catches `requests.RequestException` explicitly: it is **not** a `URLError`, so before that a `ConnectTimeout` skipped the retry loop entirely and escaped to the caller. Note `MAX_ATTEMPTS` (per HTTP request) is a different budget from `MAX_BLACKLIST_RETRIES` (per query per pass) — they multiply, though not on the 403 path: a 403 is a *response*, so `run_request` returns it on the first try and only the outer budget spends.
- `IPChanger.check_bazos_blacklisted` / `renew_ip_bazos_ok` **no longer exist** — deleted, not merely unused (`renew_ip_bazos_ok`'s validation was that same misleading probe). Stale references survive in `.github/copilot-instructions.md`, `docs/research/proxies/PROXY_ROTATION.md`, `docs/backlog/BACKLOG_IDEAS.md` and `docs/backlog/PROMPTS.md`; treat them as history, not as an API. `renew_ip_and_check_new` / `try_get_current_ip` / `skip_1st_renew` / `MAX_RENEW_ATTEMPTS` / `ROTATION_DEADLINE_SECONDS` are gone the same way — the NEWNYM-and-verify rotation they made up was replaced by `rotate_circuit` (see IP rotation above). `IPChanger.get_current_ip` retains its retries and `(20, 15)` connect/read timeout: the connect budget has to cover Tor **circuit construction**, and a flat 10 s timed out in production right after a rotation. It still raises when every attempt fails — `check_ip_local` deliberately propagates that so the pass is skipped, since not being able to see our own egress means the transport is down.
- URL generation must use model helpers (`Section.full_url`, `Category.full_url`, `Query.url`) — never rebuild URLs ad hoc.
- `Query` has DB constraints: `price_lower <= price_upper`, and `section`/`category` are mutually exclusive.
- Use the `logging` module (`logging.getLogger(__name__)`) — not `print()`. App loggers are configured in `settings.py` (INFO → console + DB).
- For scraping changes, update both `create_url_*` and `run_query` in `BazosScraper` and validate against `bazos/tests/test_gen_url.py`.
- **Dead code is excluded on purpose** — the authoritative list is the `exclude` blocks in `pyproject.toml`, and **the two tools' lists are not identical**. Both exclude `bazos_scraper_click.py`, `notifier.py`, the Slack/Email/Calendar senders, `old_tests/`, `experiments/`, `bazos_app_decomplied/`, `data_export_23_3_2024/` and migrations; **mypy alone** additionally excludes `selenium_driver.py`, `ip_changer/openvpn.py` and `verify_ip_changer.py` (gitignored). Don't "fix" lint or types in any of them. Note `selenium_driver.py` and `bazos_scraper_click.py` no longer *import*: selenium was dropped from the dependencies in the Django 5.2 / Python 3.12 upgrade, since its only live use was a `TimeoutException` in `BazosScraper.run_request` that a `requests.Session` cannot raise. They are kept as history, and ruff still reads them statically, which needs no package installed.

## Environment

Copy `.env.sample` to `.env`. **Only `SECRET_KEY` has no default** — everything else falls back in `settings.py`: `POSTGRES_DB/USER/PASSWORD` (`postgres`), `POSTGRES_HOST` (`localhost`), `POSTGRES_PORT` (`5432`), `TOR_PROXY_IP`/`TOR_PROXY_PASSWORD` (empty), `LOCAL_IP_SUBNET` (`0.0.0.0/24`), `IP_CHANGER_TYPE` (`TOR`), `ALLOWED_HOSTS`, `SITE_BASE_URL` (`http://localhost:8000`), `SENTRY_DSN` (empty disables Sentry), `INTERVAL_LOWER`/`INTERVAL_UPPER` (15/45 min), `ZERO_ROWS_ALERT_THRESHOLD` (2) / `ZERO_NEW_ADS_ALERT_THRESHOLD` (10) / `QUERY_FAILURE_ALERT_THRESHOLD` (3). `POSTGRES_PORT` *is* required for `docker compose` — it's interpolated into the port mapping.

The two canary thresholds are asymmetric on purpose: a live listing page essentially always parses to >0 rows, so zero rows is a near-certain defect (parser drift / blocked transport) and alerts fast; "rows parsed but no *new* ads" is indistinguishable from a quiet market, so it alerts slowly.

**Both of those are pass-wide and aggregate over *successful* queries only**, so one dying marketplace contributes nothing to either — it just stops appearing in the numerator while the healthy queries keep the totals normal. That is exactly how every Vinted query 404'd for eight days (2026-09-08 → 09-16) with both canaries green. `ScrapeRunner._check_query_failure_streaks` covers that case: `QUERY_FAILURE_ALERT_THRESHOLD` (default 3) consecutive passes in which *one* query failed outright alerts at ERROR, naming the query and its last error. It is keyed on `Query.pk` rather than the label (editing a query's text must not reset its streak), resets on any success, forgets queries that stop running, and re-alerts every N passes rather than every pass. The streak lives in memory, so a `ScrapeRunner` rebuild resets it — the same caveat the other two counters carry.

`.env.sample` is incomplete: it omits `IP_CHANGER_TYPE`, `INTERVAL_*`, `ALLOWED_HOSTS`, `ZERO_*_ALERT_THRESHOLD`, and the getyourguide vars (`GYG_DISCORD_WEBHOOK_URL`, falling back to `DISCORD_LOGGER_WEBHOOK_URL`; `GYG_POLL_INTERVAL`, default 300s). For local dev without Tor, set `IP_CHANGER_TYPE=DUMMY`.

Sleep between scraper passes is `uniform(INTERVAL_LOWER, INTERVAL_UPPER)`, doubled 22:00–06:00 Prague time via `NightMultiplier`.
