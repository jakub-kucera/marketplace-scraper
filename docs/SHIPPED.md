  which is deliberate; `iphone` is registered but named by no query's `filter_rule_names`. ⚠️ **It is not in shadow mode in production, whatever the shipped default says.**
  `PRICE_MODEL_SHADOW_MODE` ships `True`, but the Pi's `.env` sets it to `false` and query 8 names
  `price_model` in `filter_rule_names` - so the rule is live and has REJECTed **208 deliveries**

  [`PRICE_MODEL_DEFECTS.md`](backlog/PRICE_MODEL_DEFECTS.md) §12). ⚠️ **P24 shipped 2026-09-17, so
  the named gate is no longer missing — but it is not *passed*, and the obstacle has changed
  shape.** Outcomes now exist: 19,008 ads carry `removed_at`. But **the column cannot be used,
  because the sweep is writing it wrong.** `fetch_by_ids` sends 210 ids per request and no
  `limit`, so the API answers with its default page of 30 and the ~180 ids it omits are written
  as removals - production survivor counts are every one an exact multiple of 30, so roughly
  **86% of everything the sweep touches is falsely marked removed**. The error is permanent:
  `due_for_check` skips ads that already carry a `removed_at` and nothing clears the column, so
  those rows will silently enter any later outcome study. **Not fixed as of 2026-09-18.** On top
  of that `AdOutcome`, the table that would calibrate "removed = sold", holds **0 rows**, and
  `removed_at` conflates sold, withdrawn, deleted and expired by design. So a threshold still
  cannot be calibrated: not because nothing is recorded any more, but because what is recorded is
  an uncalibrated proxy that is also mostly false.
